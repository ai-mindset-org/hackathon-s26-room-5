# Предложение по организации работы — комната 5

Автор: Артём (J2PL). Это предложение, не решение — решает комната и лидер.

## Главная мысль

У нас 4 приёмочных примера и 6 рук. Куски не подерутся только если
**первые 15 минут потратить на контракт**, а не на код. Контракт — это
две вещи: как выглядит одна находка и как модуль подключается к ядру.
Дальше все пилят параллельно и не читают чужой код вообще.

## Контракт

### 1. Находка — одна структура на всех

```python
@dataclass
class Finding:
    rule_id:   str   # "п.3", "правило 1" — как в чеклисте заказчика
    rule_text: str   # текст правила дословно
    where:     str   # "spec.md:3" или "вал-102 · диаметр_мм"
    quote:     str   # цитата из артефакта — то самое место
    what:      str   # что не так, одной фразой
    severity:  str   # "нарушение" | "вопрос"
```

`quote` и `where` обязательны. Заказчик должен пойти править не переспрашивая —
без цитаты и адреса отчёт бесполезен.

### 2. Результат прогона

```python
@dataclass
class Report:
    findings:  list[Finding]
    artifacts: dict[str, str]   # имя файла -> содержимое (для обезличивателя)
```

`artifacts` нужен, потому что обезличиватель отдаёт не находки, а два файла:
обезличенный текст и `mapping.json`. Остальные модули оставляют его пустым.

### 3. Модуль = папка + два метода

```python
# checkers/<имя>/checker.py
NAME = "config_rules"

def matches(inputs: dict[str, str]) -> bool:
    """Мой ли это вход? Смотрим на имена файлов."""

def check(inputs: dict[str, str]) -> Report:
    """inputs: {имя файла: содержимое}"""
```

**Реестра модулей в общем файле НЕТ.** Ядро само обходит папку `checkers/`
и подхватывает всё, где лежит `checker.py`. Общий список — главный источник
конфликтов в PR, поэтому его не будет.

## Кто что берёт

| Кто | Кусок | Папка | Пример |
|---|---|---|---|
| Вадим (лидер) | ядро: `Finding`, `Report`, автозагрузка модулей, CLI | `core/` | — |
| участник | текст против чеклиста (LLM + якорь на место) | `checkers/text_checklist/` | 01 |
| участник | конфиг против правил безопасности | `checkers/config_rules/` | 02 |
| участник | замеры против допусков (чистая арифметика) | `checkers/tolerances/` | 03 |
| участник | обезличивание + `mapping.json` + обратный прогон | `anonymizer/` | 04 |
| участник | прогон `examples/` + рендер отчёта + демо | `runner/` | все |

Один человек — одна папка. В чужую папку никто не пишет. Все, кроме ядра
и раннера, работают только со своим примером и доводят его до зелёного.

## Шаги по времени

**10:30–11:00 · интервью.** Слушаем заказчиков. Главные вопросы: что дороже —
пропустить нарушение или получить ложное срабатывание; где живут правила;
что должно стоять в строке отчёта, чтобы пойти править не переспрашивая.

**11:00–11:15 · лидер выкатывает скелет.** `core/` с пустыми `Finding`, `Report`,
автозагрузкой и CLI `python -m core <папка-примера>`. Мержит сразу в main, даже
если внутри заглушки. Всем остальным нужен якорь, а не красота.

**11:15 · разбор кусков.** Заводим issues, по одному на модуль. Кто взял — пишет
в issue. Каждый форкает, ветка `КОД/имя-куска`.

**11:15–12:30 · параллельная работа.** Каждый доводит СВОЙ пример до совпадения
с `expected.md`. PR открываем сразу, как модуль впервые запустился, не ждём
готовности. Лидер мержит по мере поступления и после каждого мержа гоняет `examples/`.

**12:30–13:00 · сборка.** Раннер печатает «прошло N из M». Чиним то, что красное.
Кто закончил свой кусок раньше — не берёт новый модуль, а идёт помогать красному.

**13:00–13:10 · демо.** Один прогон всех четырёх примеров на экране + отчёт
глазами заказчика. Показывает раннер, комментирует лидер.

## Два правила, которые сэкономят нам час

1. **Ложное срабатывание дороже пропуска.** В примерах это заложено явно:
   `API_TOKEN_FILE` не секрет, толщина 11.96 при допуске −0.05 не брак.
   Модуль, который ловит лишнее, проваливает пример так же, как модуль,
   который не ловит ничего.

2. **Ветка от свежего main.** `git pull --rebase upstream main` перед каждым
   пушем. Force push в общие ветки — нет.
